# Building a painting world

Choose the experience from the painting. A street may invite a walk, an interior may work best at room scale, and a spatial tableau may work from a few deliberate viewpoints. A new world can use painted meshes, projected layers, instanced brushstrokes, or a mix. Starry Night demonstrates one rendering approach and provides test cases for problems that can recur with any approach.

## Start with the painting and a short route

1. Identify the exact work and scan already used by the gallery. Record the composition, landmarks, color and light relationships, and what the viewer should notice first. Decide which back sides, undersides, and spaces outside the canvas the viewer can see and how to treat them. Keep source images in `assets/` and ship only the runtime derivatives needed under `public/`. Track new source and derivative hashes in [asset provenance](../assets/PROVENANCE.md).
2. Pick the arrival pose, usable space, viewing distance, and interaction before investing in the final renderer. Sketch a route from gallery entry through the reference view, the closest useful view, the most oblique view, and back to the gallery. If movement is part of the experience, include an actual trip around the space. If the painting has an interaction, describe what it should look or feel like and how the viewer discovers and stops it. The painter camera is a reference pose. A painter-spot challenge, flight, reactive brushwork, and positional audio are design choices.
3. Build a small slice with the intended scale, a signature landmark, one hard viewing angle, and representative lighting or layering. Compare a fixed capture with the scan, then look around in immersive VR before building the rest. Capture the rendering path and expected worst view on Quest early. Use that evidence to choose an acceptable quality and performance target for the world.

Record the reference, chosen interaction, test route, and acceptance criteria in the world’s card. Keep a reproducible comparison capture as the scene evolves. The existing [capture script](../scripts/capture-shot.ts) can record a served world with `?painting=<id>&painter&diag&shot&noanim` when the world exposes the standard diagnostics. Use [the Starry Night fidelity test](../tests/e2e/fidelity.spec.ts) as an example of a repeatable comparison and choose thresholds for the new scene.

For Café Terrace at Night, start from the existing registry entry and gallery frame. The amber terrace against the blue street and sky, the awning and façade, and the receding pavement can anchor the visual slice. Test a short ground-level approach as one candidate. Check the façade at an oblique angle and the awning from below before committing to a treatment for them. Choose how far the viewer can explore or whether the interior is visible as part of the design. [Scan and frame provenance](../assets/PROVENANCE.md)

## Fit the gallery and portal lifecycle

- Use the stable ID in [the painting registry](../src/paintings/registry.ts), with the existing frame and provenance metadata. A live entry supplies a lazy world loader. Exercise both gallery entry through the frame and `?painting=<id>` direct boot. Test the gallery return, a second visit, and a failed load. The gallery is the recovery destination and the frame’s coming-soon state should match actual availability.
- [WorldModule](../src/paintings/world-module.ts) defines `build`, `update`, `dispose`, `spawnPose`, `painterSpot`, and `painterCamera`. [World binding](../src/main.ts) wires the active handle into movement, render, settings, return, and audio. Provide a safe spawn for desktop and XR, consistent ground and bounds, and an authored reference camera. The current shell and portal consume a `StrokeBatch`, including its atlas and reveal data. A mesh-led or layered scene may only need strokes where they contribute visually, such as the transition. If the scene needs a different reveal or a different handle, prototype that shared seam and regression-test Starry Night and the gallery through it.
- Put geometry in a world-owned root and make ownership explicit for textures, materials, audio, and diagnostics. Dispose partial as well as successful builds, and leave the shared atlas to its owner. If a world needs a late resource for its first visible frame, use the readiness path so the switcher can prepare it. Check repeat visits for leftover scene nodes, stale bindings or poses, duplicated audio, and growth in retained resources.
- Treat the portal as visible while the destination loads. Use the existing slicer for expensive CPU work and keep the same result when drained at direct boot. A lazy import is only one part of the wait. Check decoding, build slices, the first shader compile and GPU upload, and reveal separately. Time cold and warm entry and first and repeated return. Inspect the longest frames along with total duration. Inject failed and delayed loads, including late completion, and confirm that the notice, recovery, and subsequent retry work. A continuous transition gives the user feedback while real work completes. ## Collect release evidence

1. **Repository and served build.** Use `make checkall` while iterating and `make checkall-ci` before release. Keep runtime assets within the [asset](../assets/PROVENANCE.md) and [bundle](../scripts/bundle-budget.ts) checks. Exercise the served build and its base-relative assets. For an update or offline change, run `make update-ab`. On release, confirm that the live build ID matches the candidate.
2. **Desktop and emulated immersive VR.** Use [the Playwright harness](decisions/0001-xr-emulation.md) for repeatable poses, screenshots and input through the real UI. Start with focused checks for the world, then run `make e2e` for shared integration and release. Use hardware-backed Chromium, record the renderer, and keep the portal timing spec in its serial project. For a load-sensitive run, use a booked host and record one-minute load before and after. For a visual or interaction regression, reproduce the old failure or use a negative control that proves the assertion can fail.
3. **Physical Quest.** Run the marked route in Quest Browser on the candidate build. Record commit and build ID, settings, refresh request, foveation, enabled features, segment marks, and actual delivered frames. Collect `?perf`/diagnostics and Quest Browser VrApi separately. Use fixed settings for A/B comparisons, repeat the worst view, and include gallery, portal, and return if claiming the whole route. Capture owner feedback on the look, comfort, interaction and audio that the build offers. Keep missing evidence visible. Desktop pixels, IWER input, app frame callbacks, and the headset’s delivered FPS each answer different questions. [Quest recording protocol](headset-test-2026-11-11.md) · [Release measurements](perf.md#sc1-release-candidate-route-p72-2026-11-13)

The Starry Night acceptance run used Adaptive-72, fixed level 5, foveation Off, and audio on. The first marked run fell short of five minutes and dipped below the floor in force at the time. On the full 5 min 42 s repeat, the median Quest Browser reading was 28 fps and the minimum was 22 fps. Paul approved the revised 22 fps floor for that release. Use the current project requirements and the new world's own Quest route and quality tradeoffs for its acceptance.
